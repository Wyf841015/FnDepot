> 智能扫描系统，精准识别已卸载应用、网盘挂载和 Docker 的残留目录及重复文件，一键安全清理 - Node.js 版。

  应用名从路径里取，不写死，换安装目录名也算得对。

- 升级说明：手动启动过的机器，`<vol>/@appcenter/fnclearup/data/` 下可能残留
  `schedule.json`、`dup/`、`empty_dir/`、`schedule_reports/`，
  这些已在本机迁移到 `<vol>/@appdata/fnclearup/data/`，原目录内容未删除。
- 新增测试 `tests/test_pkgvar.js`（6 项）：路径反推、软链/非安装目录返回 null、
  env 优先（含 trim 与空白 env）、无 env 时兜底、manifest 与 data 目录同源。

## v0.15.0 更新

本次是**商店版本**（上一版 0.13.1）。中间 0.14.x 的改动全部收进这一版，下面是完整清单。

### 新增：内核清理

清理回收分组新增第 6 个 tab —— 盘点本机所有已装内核，勾选清理老内核。

| 项 | 说明 |
|---|---|
| 能看见的 | 每个内核的版本、运行中/GRUB 默认启动/建议保留徽章、整组体积、关联的 dpkg 包 |
| 体积 | `/lib/modules/<ver>` + 该版本所有 `/boot` 文件，实测本机 10 套共 3.0 GB |
| 顺带清理 | APT 下载缓存、残留配置包（`dpkg` 状态 `rc`） |

**四条硬边界，测试逐条锁死：**

1. 正在运行的内核永远删不掉（前端不给勾 + 后端删前再拦一次）
2. 只接受扫描结果里真实存在的版本，包名一律来自 `dpkg` 实测
3. 必须带 `confirm: 'PURGE'` 才执行
4. 同一时间只允许一个清理任务

### 内核删除前先让 apt 自己预演

`apt-get purge` 的连带范围**不是固定的**。实测对比：

| 场景 | apt 实际会删 |
|---|---|
| purge 一套**老**内核 | 正好 3 个包（image + headers + modules-trim），零连带 |
| purge **正在运行**的内核 | **6 个包** —— 连 `linux-image-amd64`、`linux-headers-amd64`、`linux-modules-trim-extra` 这些**元包**一起带走 |

所以现在点「清理选中」时会先跑 `apt-get -s purge`（只模拟），把 apt 自己报告的计划
原样摆给你看。预演里出现范围外的包 → 必须额外勾选确认；出现运行中内核的包 → 直接拒绝。

另外修了三个会伤到系统的地方：

- **包名匹配从子串改成精确** —— 原来 `includes('-6.18.18-')` 会把 `6.18.18-trim` 的包也吃掉，删一个内核连带删另一个
- **unhold 失败要恢复 hold** —— 不留「本来锁着、现在能删」的状态
- **绝不 SIGKILL 正在跑事务的 dpkg** —— 改用只收集输出、超时只标记的自实现，避免把 dpkg 数据库搞成半配置

### 修复：多选清理报「有任务正在进行」

预演本来也占了清理锁，导致你点确认时撞上自己刚才那次预演。现在锁只在真删时占用，
预演期间前端直接禁用确认按钮，预演改并行（8 个版本 12s → 约 2s）。

### 修复：全选清理等很久然后失败

原来每套内核单独跑一次 `apt-get purge`，实测单套 29s，而且**每套都要跑一遍 `update-grub`**。
8 套串行 ≈ 200s+，直接顶到 fnOS 网关 `location /app/` 的 `proxy_read_timeout 300s`，
浏览器收到 504。

现在合并成**一次 apt 事务**：dpkg 只跑一轮、`update-grub` 只跑一次。实测 2 套 43s（原来 58s+）。

顺带把结果判定改对了：以「删完再扫一遍，看文件还在不在」为准，不再只看 apt 退出码
（apt 可能因 initramfs warning 返回非 0，但包其实已经删干净）。

### 修复：那个 16.0 KB 根本不是 APT 缓存

界面一直显示 `APT 下载缓存：16.0 KB（0 个 .deb）`，点了清理也不变。查下去发现：

```
/var/cache/apt/archives/ → 0 个 .deb，du 总计 16K
```

16 KB 是**目录的 inode 块（12K）+ `partial/`（4K）**，`apt-get clean` 早就清干净了 ——
这个数字在骗人。现在只统计 `*.deb` 总大小，`0 个 .deb` 时显示 `0 B` 并直接提示"已经是空的"。

残留配置包也从「提示你自己敲 `dpkg --purge`」改成**能点的按钮**，而且不再只查 `linux-*`
（本机实际有 7 个，漏了 `fuse` / `openzfs-*` / `wsdd2`）。安全约束与内核清理一致：
只对调用那一刻真的是 `rc` 状态的包下手，客户端传的包名只用来取交集。

### 修复：首页风险提示勾掉后有时还是弹

根因不是逻辑分支写错，是**偏好存的地方不可靠** —— 这个开关只存 `localStorage`，
而应用会同时跑在「应用中心 iframe」和「CEF 独立新窗口」两种上下文，
两者 localStorage 可能是不同存储分区，部分环境还会禁用或清空。

现在新增 `GET/POST /api/prefs`，偏好落到 `<TRM_PKGVAR>/data/ui-prefs.json` 作为唯一真理源，
localStorage 降级为本地缓存。首屏一律先问服务端再决定弹不弹（不做「本地优先再后台对齐」，
否则会先弹一次再收）；一次页面加载最多弹一次；保存失败会回滚勾选状态。

### 测试

全量 **598 项**通过。新增覆盖：内核包名精确匹配（防子串误伤）、删除预演、
并发预演不抢锁、单次事务、APT 缓存口径、`rc` 包边界、启动提示三层（接口/接线/真 DOM）。

## v0.14.3 更新

修「清理 APT 缓存点了没变化」，并把残留配置包从"提示你自己敲命令"改成能点。

### 那个 16.0 KB 根本不是缓存

界面一直显示 `APT 下载缓存：16.0 KB（0 个 .deb）`，点了清理也不变。查了一下目录：

```
$ ls -la /var/cache/apt/archives/
-rw-r----- 1 root root     0 lock
drwx------ 2 _apt root  4096 partial/
总计 16K，*.deb 数量 = 0
```

**16 KB 是目录本身的 inode 块（12K）+ `partial/`（4K）**。`apt-get clean`
早就清干净了，一个 `.deb` 都没有 —— 这个数字在骗人。

改法：

- 缓存量只统计 `*.deb` 的总大小（这才是 `apt-get clean` 真正能释放的）
- 目录开销单独放 `dir_size` 字段，不参与"可清理"
- `0 个 .deb` 时界面直接显示 `0 B`，点按钮只提示「已经是空的」，不发请求
- 清理后报的是**前后差值**，不是一个字节没删也说「已清理 16.0 KB」

### 残留配置包现在能直接点掉

原来只在提示里写一句「`dpkg -l | grep ^rc` 可查，可手动 `dpkg --purge`」——
等于让用户自己去敲命令。而且列出来的只有 4 个，因为它只查了 `linux-*`。

实测这台机器有 **7 个** rc 包（包本体早删了，只剩 `/etc` 下的配置）：

```
fuse
linux-image-6.1.0-9-amd64      ← x86 时代的老内核号，跟现在跑的 trim 内核无关
linux-image-6.1.0-13-amd64
linux-image-6.1.0-17-amd64
linux-image-6.1.0-18-amd64
openzfs-zfs-modules-6.12.18-trim
wsdd2
```

现在那一行后面有个 **🧹 清理残留配置包** 按钮，走 `POST /api/kernel/purge-rc`。

安全约束跟内核清理一样严格：

- **只对调用这一刻真的是 rc 状态的包下手** —— 客户端传的列表只用来取交集，
  包名一律以 `dpkg` 实时查询结果为准，绝不把前端传来的字符串当参数用
- `confirm` 必须是 `PURGE`
- 与内核清理共用同一把 busy 锁、同一套 apt/dpkg 忙碌检测
- `dpkg --purge` 走 `runUnkillable`，超时只标记不 SIGKILL（不能把 dpkg 数据库搞坏）
- 清完再查一遍 rc，用实测结果报成功/失败

实测：

| 请求 | 结果 |
|---|---|
| 缺 `confirm` | 400 `缺少确认标记` |
| 传 `bash`/`coreutils`（非 rc） | 400 `指定的包都不是「残留配置」状态（rc），已拒绝` |
| 传不存在的包 | 400 同上 |
| 真清 `linux-image-6.1.0-9-amd64` | 成功，638ms，剩 6 个 |

## v0.14.2 更新

修内核清理的两个真实故障（用户实测报告）：

1. 多选全选时提示「已有清理任务在执行」，清理失败
2. 清理单个内核时要等很久，最后仍提示失败

### 故障 1：预演占了清理锁

为了让用户看清 "apt 到底要删什么"，打开确认弹窗时会先跑一次
`apt-get -s purge` 预演。但预演**也走了清理锁**（`kernelBusy`）：

```
打开弹窗 → 后台开始预演 8 个版本（约 12s）
用户勾选同意 → 点确认  → 撞上自己那次预演 → 409「已有清理任务在执行」
```

预演是只读的（`apt-get -s` 不写系统、不抢 dpkg 锁），本来就不该占锁。现在：

- 锁只在**真删**时占用（`if (!dryRun)`），解锁同理
- 预演期间**前端直接禁用确认按钮**（`kernelState.dryLoading`），连点出去的机会都不给
- 预演的 8 次模拟改成**并行限 3 路**，从 12s 降到 2s 左右

### 故障 2：串行 purge 撞上网关 300 秒超时

原来每个内核单独跑一次 `apt-get purge`。实测**单套 29 秒**（apt 24s，而且**每套都要跑一遍
`update-grub`**）。8 套串行 ≈ 200s+，直接顶到 fnOS 网关的上限：

```nginx
# /usr/trim/nginx/conf/conf.d/trim_http_cgi.conf
location /app/ {
    proxy_pass http://unix:/var/run/trim_http_cgi.socket:;
    proxy_read_timeout 300s;      # ← 就是这里
}
```

浏览器在 300s 收到 504 / 连接中断，表现就是「等很久然后失败」。

现在改成**一次 apt 事务删掉全部选中内核**：

- 所有包合并成一条 `apt-get purge <10+个包>`，dpkg 只跑一轮，`update-grub` 只跑一次
- hold 住的包一次性全部 `apt-mark unhold`，失败再整体 `hold` 回去
- 实测：**2 套 = 43 秒**（apt 本身 38s），原来串行要 58s+；8 套预计 1 分钟出头

### 顺带：结果判定口径改对了

以前按 `apt` 的退出码判断成败。但 apt 可能因为 initramfs warning 返回非 0，
包其实已经删干净了 —— 那样会误报失败。现在**以「删完再扫一遍，看文件还在不在」为准**：

```js
const gone = !left || !left.has_files;   // 文件没了才算删掉
if (gone) freed += item.k.size;          // 释放量也只算真删掉的
```

包删了但 `/lib/modules` 或 `/boot` 还留着 = 半清理，单独在 `leftover` 里报出来。

### 顺带：补上日志（以前是零日志）

内核清理这条路径原来一行日志都没有，出问题只能靠猜。现在会记：

```
[kernel] apt-mark unhold 2 个包 → code=0
[kernel] purge 6 包 / 2 套 → code=0 ms=38331
[kernel] apt 错误: ...          ← 失败时把 stderr 记下来
```

### 实测记录

| 操作 | 结果 |
|---|---|
| 并发两次预演 | 都返回 200，不再有 409 |
| 真删 1 套（旧实现） | 29s，成功 |
| 一次事务删 2 套 | 43s，成功，释放 483.8 MB，leftover 空 |
| 全量测试 | 591/591 |

## v0.14.1 更新

修一个让人抓狂的小毛病：**首页风险提示勾掉之后，有时还是会弹**。

### 根因不是逻辑分支写错，是偏好存的地方不可靠

以前这个开关只存 `localStorage`。而 fnOS 上同一个应用会同时出现在两种上下文里：

| 打开方式 | 上下文 |
|---|---|
| 应用中心点进去 | iframe（frame 模式） |
| 新窗口打开 | CEF 独立窗口 |

两者的 `localStorage` **可能落在不同的存储分区**，部分环境还会直接禁用或清空。
于是「同一个开关，这次生效、下次又弹」—— 看起来像随机，其实是换了上下文。

### 改法：服务端文件做唯一真理源

- 新增 `GET/POST /api/prefs`，偏好写到 `<TRM_PKGVAR>/data/ui-prefs.json`
  （跟 `scan_exclude.json` 同一层，tmp + rename 原子写）
- `localStorage` 降级为**本地缓存**，只用于首屏快速判断
- **首屏一律先问服务端再决定弹不弹**，不做「本地优先、再后台对齐」——
  那样在「本地缓存说弹、服务端说关」时会先弹一次再收，用户看到的就是
  "我明明关了它又弹了一次"。宁可等一次同机往返（2~5ms，最长 2.5s 超时）
- 一次页面加载**最多弹一次**（`_startupWarnShown`），`showStartupWarning()`
  自身也幂等（已在显示就不重复初始化，否则倒计时被重置成 3 秒，看起来又像弹了一次）
- 两只勾选框改成**显式传来源**（`setStartupWarnFrom('modal')` /
  `setStartupWarnFrom('setting')`），不再靠「谁的值和旧值不同」来猜 ——
  那种猜法在两框状态不一致时会选错
- 落盘失败**必须回滚**勾选状态与本地缓存，不允许出现「界面显示关了、其实没存上」

### 顺手清掉一处过时注释

`showStartupWarning` 上面的注释写着「删按钮时会再调一次，见 `_bumpStartupWarning()`」，
但全文根本没有这个函数 —— 读代码的人会以为存在一条隐藏的重复弹出路径。

### 验证

新增三个测试文件，覆盖三层：

| 文件 | 覆盖 |
|---|---|
| `tests/test_startup_warning_pref.js` | `/api/prefs` 读写、默认值、白名单、类型规整、坏文件容错、前端接线 |
| `tests/test_startup_warning_dom.js` | happy-dom 真跑整页：服务端优先、两支路分歧、一次加载只弹一次 |
| `tests/test_startup_warning_always.js` | 开关语义 + 两只勾选框始终同步 + 保存失败回滚（按新设计重写） |

其中最能对上用户体感的一条：**本地缓存说「弹」而服务端说「不弹」→ 一次都不能弹**。

## v0.14.0 更新

新增「清理回收 → **内核清理**」tab：把 `apt` 装上的旧内核整组清掉。

### 为什么需要它

fnOS 每次系统升级都会装一整套新内核（`image` + `modules` + `headers`），**旧的不会自动清**。
本机实测攒了 **10 套、共 3.0 GB**（`/boot` + `/lib/modules`）。旧内核堆着不只是浪费空间：
`/boot` 往往是独立小分区，塞满之后系统更新会直接失败，而且只报「磁盘空间不足」，
根本联想不到是旧内核。

### 做了什么

- 扫 `/lib/modules/<版本>` 与 `/boot/*<版本>*`，配合 `dpkg-query` 把每个版本的
  `linux-image-* / linux-modules-* / linux-headers-*` **整组**找出来
- 表格列出：版本 / 状态徽章 / 体积 / 关联包；体积 = modules 目录 + 该版本所有 `/boot` 文件
- 「✅ 推荐清理」勾选除「正在运行」和「建议保留（最新一个备用）」之外的全部
- 清理走 `apt-get purge`（带 `Dpkg::Options::=--force-conf*` 防交互卡住），
  hold 住的包会先 `apt-mark unhold` 再删
- 顺带给出 APT 下载缓存（`/var/cache/apt/archives`）体积与一键清理，以及 `rc` 残留配置包清单

### 删除前先让 apt 自己预演一遍（最重要的安全设计）

`apt-get purge` 的连带范围**不是固定的**，所以不能靠「我算好了包名」就下手。
本机实测两种情况的差别很大：

| 情况 | apt 实际会删 |
|---|---|
| purge 一套**老**内核（c788） | 正好 3 个包（image + headers + modules-trim），零连带 |
| purge **正在运行**的内核（c1126） | **6 个包** —— 连 `linux-image-amd64`、`linux-headers-amd64`、`linux-modules-trim-extra` 这些**元包**一起带走 |

第二行就是隐患：真删掉元包之后，以后再升级内核就不会自动装了。所以现在的流程是：

1. 点「清理选中」→ 前端先调 `dry_run: true`
2. 后端对每个版本跑 `apt-get -s purge`（**只模拟，不写系统**），把 apt 自己报告的
   `Purg xxx` 列表原样返回
3. 弹窗里逐条列出「apt 会删：…」，用户看到的是 apt 的真实计划，不是我算的
4. 如果预演里出现**范围外的包**（元包之类）→ 弹窗多出一个勾选框，必须单独确认才放行；
   没确认后端也会拒绝（`needs_extra_ack`），返回 `allow_extra_removals` 才能继续
5. 预演结果里只要出现**正在运行内核的包** → 直接拒掉，不进执行队列

### 四条硬边界（不可绕过）

1. **正在运行的内核永远不可删** —— 前端不给勾，后端删前再拦一次
2. 只接受**扫描结果里真实存在**的版本；包名一律来自 `dpkg` 实测，
   不接受前端传来的任意包名/路径（防命令注入），并且 `spawn` 数组参数调 apt，全程不过 shell
3. 必须带 `confirm: 'PURGE'`；弹窗里还要勾选确认
4. 同一时间只允许一个清理任务（`busy` 锁）

### 删掉 GRUB 默认启动的那个内核，开机会怎样

本机实测：`/etc/kernel/postrm.d/zz-update-grub` 存在，所以 purge 内核后
grub.cfg **会被自动重新生成**。此时 `GRUB_DEFAULT` 指向的那个菜单 id 消失，
GRUB 会回退到**第一条菜单**。

而本机 grub.cfg 的第一条是：

```
menuentry 'FNOS GNU/Linux'                                   ← 第 0 条，回退落点
menuentry 'FNOS GNU/Linux, with Linux 6.18.18.c1126-trim'     ← 正在运行的内核
```

第 0 条加载的正是 `6.18.18.c1126-trim`（同文件里 c1126 出现 11 处，排在最前）。
所以即使把 `6.12.18-trim`（当前 GRUB_DEFAULT）删掉，下次开机仍然启动
**正在运行的这个内核** —— 不会起不来。

即便如此，界面上还是会给「GRUB 默认启动」打独立徽章，删它时弹窗明确提示，
不让你在不知情的情况下改掉默认启动项。

### 一个容易踩的坑：GRUB 默认启动的可能不是你正在跑的内核

本机实测 `GRUB_DEFAULT` 指向 `gnulinux-6.12.18-trim-advanced-…`，
而正在运行的是 `6.18.18.c1126-trim`。所以表格里会给「GRUB 默认启动」单独打一个徽章，
选中它时确认弹窗会明确提示：**删掉之后下次开机会回退到启动菜单第一条**（不会起不来）。

### 顺手修掉的两个测量 bug（自己写测试时抓到的）

- `dpkg` 的 `Status` 第三字段才是安装状态。用 `statusRaw.includes('installed')` 判断，
  会把 `hold ok not-installed` 也算成已安装 —— 本机 345 个从未安装的候选内核包
  因此被当成"已装内核"，列表瞬间变成 369 行
- `du -sk` 读不了 `archives/partial`（属主 `_apt`）时退出码是 1，
  按退出码判成败会把 175 MB 的 APT 缓存报成 0 B。只要 stdout 能解析就该采信

## v0.13.1 更新

本版只做一件事：**把「用户清理」删账号前的判据补严**。0.13.0 上线后真机上查出一处
会让「正在运行的应用」被误删账号的漏洞，这版堵掉，并顺带覆盖 Docker 容器。

### 漏洞：账号名 ≠ 应用名，导致应用账号被判成「可删」

真机实例：`netease`（网易云 API）是**正在运行**的应用，但它的账号叫 `docker-netease`
（uid 984）。原先只做 `id -u <应用名>` 反查，`id -u netease` 查不到就直接放过，
「应用仍在安装中」这条判据完全没生效 → 该账号在列表里显示**可删**。

删掉的后果：`/volN/@appcenter/<应用>` 整棵树变成孤儿 uid，应用中心升级 / 卸载失败。

| 应用名 | 实际账号 | 为什么原来漏掉 |
|---|---|---|
| `netease` | `docker-netease` | 账号名带 `docker-` 前缀，`id -u netease` 失败 |
| `fnm3u8dl` | `package` | 靠系统账号保护兜住 |
| `nodejs_v22` | `admin` | 靠系统账号保护兜住 |
| `Lucky` | `root` | 靠 uid 0 判断兜住 |

**修法**：新增 `installedAppDirByUid()` —— 对每个已安装应用，按
`<卷>/@appcenter/<应用名>`（以及 `/usr/local/apps/<应用名>`）的 **owner 反查 uid**，
名字查不到时用它兜底。app 目录的 owner 才是权威判据。

### 新增：Docker 容器占用判据

删账号前再查一层「是不是 Docker 容器在用」。**已停止的容器没有进程**，原来靠
`activeCount > 0` 完全拦不住 —— 删掉账号后容器再起来就写不进挂载目录了。

三条来源，任一命中即不可删：

| 来源 | 说明 |
|---|---|
| 运行中容器 | 读 `/proc/<pid>/status` 的 `Uid:` —— 最权威，能穿透镜像内用户名 |
| `Config.User` | 写成数字 uid 时（`1000` / `1000:1000`）直接采信 |
| 挂载点 | bind 挂载目录 / named volume 挂载点的 owner |

> `Config.User` 写成**用户名**时刻意不猜：容器里的用户名按**镜像内** `/etc/passwd`
> 解析，宿主同名账号未必同一 uid，硬拦会误伤。宁可漏判。

`docker` 命令不可用 / 无权限时，状态栏会明确提示「⚠️ Docker 未检测（原因）」，
不会把「查不到」静默当成「没占用」。

### 两条删除路径都覆盖

只在「用户清理」页挡住是不够的 —— 从「应用残余清理」勾「同时删除用户」进来
照样能删。`POST /api/delete` 的 `delete_users` 分支现在走同一套判据
（动态 import 取 `users.js`，避免模块循环依赖），命中则进 `users_failed` 不执行 `userdel`。

### 列表新增 Docker 标记

被 Docker 占用的账号在「类型」列多一个 **Docker** 徽章，鼠标悬停显示容器名与占用来源；
该行勾选框禁用，全选也不会勾上。

### 测试

- 新增 `tests/test_users_docker.js` 23 项：假 `docker` 脚本塞 PATH（绝不碰真 Docker），
  覆盖三条占用来源、两条删除路径端到端、`available=false` 降级、目录 owner 反查
- `test_users_ui.js` 补 2 项：Docker 徽章渲染 + 全选跳过
- 全量 **541/541 通过**

## 三个分区新增删除：相似 · 异常 · 重名

原先 6 个分区里只有去重/空目录/大文件有删除功能，这三个扫出来的结果清不掉。

| 分区 | 选择方式 | 说明 |
|---|---|---|
| 相似 | 逐文件 | 每个文件独立勾选，删除后重新扫描 |
| 异常 | 逐文件 | 空文件 / 无效链接 / 损坏文件 / 下载残留都可删 |
| 重名 | **按组** | 勾一组 = 删该组除第一份外的所有副本 |

重名分区特意做成**组粒度**：逐文件勾选时「全选」会把每组仅存的那一份也删掉，
组粒度天然保证至少留一份。只有一份的组，勾选框直接禁用。

### 删除方式与其他分区一致

- **放到回收站**（默认）→ 移至 `/volN/UID/.@#local/trash`，可恢复
- **永久删除** → 直接删除，选了要额外勾一次「我已确认」

确认弹窗会显示来源分区、文件数量、占用空间、路径预览（前 20 条 + 汇总），
以及该分区特有的提醒（重名「保留每组第一份」/ 异常「只删链接本身」/ 相似「不等于重复」）。

### 删除安全

- 复用既有的 `partitionDeletable`：拦 `@appcenter`/`@appdata` 等系统目录与卷内回收站，
  非 `/vol*` 路径一律拒绝
- **无效链接只删链接本身** —— 实测 `rmSync`/`renameSync` 都不跟随符号链接，
  删除死链不会连带删掉它指向的目录（已实测：链接目标目录及其内容完好）
- 回收站同名冲突自动加 `_1`/`_2` 后缀，不会覆盖已有文件
- 路径已被其他程序移走算「已移走」而非失败；有失败或被拦截时结果用错误样式提示，
  不会显示成全成功

### 顺带修掉的既有缺陷

新端点的回收站路径映射最初写成 `UID` 段必须纯数字，但 fnOS **网盘挂载的 UID 形如
`1000-1-0985cb1`**，导致 `/vol02` 下的文件永远提示「路径格式不支持回收站」。
改为数字开头（`\d[^/]*`）—— 既兼容网盘后缀，又不会把 `/vol1/a/b` 里的目录名 `a`
误当成 UID。

## 相似文件改为按组显示，每组推荐保留一个

原先所有相似文件铺成一张大表，靠「组」列的数字区分 —— 组内成员在视觉上完全散开，
也没有「这一组该留哪个」的提示。现在改成**组卡片**：

```
┌ 组 1   3 个 · 最相似 100% · 组占用 24.0 MB · 可释放 16.0 MB        [🖼 对比]
│  ★ 推荐保留   照片.png              8.0 MB   100%   /原始/照片.png
│               文件名无副本标记(其余 2 份带 副本 等后缀)
│  ✕ 删除       照片 - 副本.png      8.0 MB   100%   /备份/照片 - 副本.png
│  ✕ 删除       照片 - 副本(2).png   8.0 MB   100%   /临时/照片 - 副本(2).png
└
```

组头的勾选框 = 删掉本组除推荐外的全部；新增「✓ 全选各组」按钮一次处理所有组。

### 推荐依据（每条都会显示在界面上）

1. **文件名无副本标记** —— 带 `(1)` / `-副本` / `_copy` / `backup` 的基本可断定是复制出来的
2. **修改时间新** —— 都干净时，新的那份通常是后来整理/导出的结果
3. **体积更大** —— 同类文件中更大的往往是更高画质/分辨率
4. **路径层级浅** —— 深拷贝目录（backup/备份）里的让位给浅层的
5. **路径字典序** —— 以上全同时的兜底，保证同一份数据每次推荐结果一致

相似 ≠ 重复：dHash 距离小只代表视觉接近，内容仍可能有差异，所以推荐只决定**默认勾选谁被保留**，
最终删不删由用户决定。推荐理由直接显示在推荐行下方，可以据此推翻推荐。

## 扫描与删除：不再让用户扫完才发现删不掉

### 大文件扫描跳过系统目录（修「扫描后选中删除全部失败」）

扫整卷时，原先把 `/vol3/@sysappmeta/ai-manager/models/*.onnx` 这类**应用模型文件**
也列进「大文件」清单 —— 用户看到「占了我 5.8G」，勾选去删，删除端点被安全闸门
全部拦下：

```
扫描返回 20 个 → 删除 deleted=2 / blocked=8 / skipped=8
```

用户体验就是「全部失败」，还白折腾一次扫描。

现在扫描阶段就**整棵剪枝**掉 fnOS 系统目录与回收站（`@appcenter`/`@appconf`/
`@appdata`/`@apphome`/`@appmeta`/`@appshare`/`@apptemp`/`@sysappmeta` 与 `.@#*`），
扫 /vol3 的候选数从 36 降到 17，结果列表里再没有用户无权清理的文件。状态栏会显示
「已跳过 N 个系统目录/回收站（应用安装文件与运行数据，不占用可清理空间）」。

剪在**下钻之前**而不是遍历完再过滤：一是省掉 fuse 挂载系统目录的上万个 inode 遍历，
二是列表里不再混着删不掉的东西。应用自身的数据目录不剪（那占用的是用户的盘，
用户有权知道），删除端的闸门一点没放松。

实测：扫整卷 /vol3 候选 36 → 17，跳过 20 个系统目录；对可删目录做删除，
trash 与 permanent 两种模式均 **100% 成功**。

### 只读卷：扫描时就说清「这个卷删不掉」

用户报的「扫描后选中删除全部失败」，真根因是 **`/vol2` 以 btrfs (ro) 挂载**，
其上 82G 视频全在 `/vol2/1000/video`。扫描照常列出 57 个「大文件」，勾选全删，
每个都 `EROFS: read-only file system` —— 显示出来就是「全部失败」。

应用没做错删除逻辑，错在没告诉用户：

1. **扫描阶段不告知该卷只读** —— 用户白勾一遍。状态栏现在会显示
   `⚠ /vol2/1000/video 为只读卷（卷以只读方式挂载，无法写入或删除任何文件），其下文件无法删除`
2. **删除失败时把英文错误码原样透出** —— 用户看到 `EROFS: read-only file system`
   会以为是程序坏了。现在翻译成 `⛔ N 个文件所在卷为只读，无法删除（EROFS）· 成功 M/K`，
   整卷都删不掉时会补一句「本卷一个都删不掉」

可写性探测不用 `access(W_OK)`：**fnOS 的 trimacl 会把目录 mode 显示成 000**
（实测 `/vol2/1000` 是 `mode=0o0`），对可写卷也返回 false，完全不可信。唯一可靠的办法
是真的写一个临时文件再删掉，每个扫描根试一次。探针删不掉时会如实上报 `leftover`，
不在用户目录里静默留垃圾。

### 容器 / 系统缓存分区：切进来就自动扫描

原先切到面板必须手动点「扫描」。改之前先测了两个接口的耗时，差了 100 倍，策略不同：

| 接口 | 实测耗时 | 策略 |
|---|---|---|
| `api/docker/stopped`（容器） | **0.1s** | 每次切换都重扫 |
| `api/sysclean/scan`（系统缓存） | **首次 16s / 缓存后 3.7~4.2s** | 限流：没扫过时自动扫，60 秒内切走再切回来沿用上次结果 |

容器的启停由用户随时改变，看到「上次扫描时的快照」几乎必然是错的，而 0.1s 的代价可忽略，
所以每次都扫。系统缓存区要 stat 上千个目录，来回切 tab 每次等十几秒不能接受，所以限流；
手动「扫描缓存」按钮始终能强刷。

顺带修掉三处：

1. **`api/sysclean/scan` 的超时从默认 15s 提到 90s**。实测最坏 16s，默认 15s 意味着
   慢的那一半必然报 `signal is aborted without reason`。手动点扫描同样会超时，
   用户只会当成自己网络问题 —— 既有 bug，被自动扫描放大成了必然发生
2. **两个扫描函数都加了防重入**。自动扫描和用户手点很容易撞在一起，两个响应同时往同一个
   列表渲染，后到的覆盖先到的，用户看到的是随机一份数据
3. **缓存分区空状态的提示语换掉了**。那个分区只有「清理缓存」按钮，没有「扫描」按钮，
   原来写「点击『扫描』按钮获取详情」，用户在这个分区找不到那个按钮，只会干等着

## 去重扫描启动失败：不再留一个不动的进度条

用户加了 `/vol1/1000/music`（该目录在本机不存在）后点「开始扫描」。后端返回
`400 { error: '目录不存在: /vol1/1000/music' }`，前端弹了 toast、状态栏也写了 ❌ ——
但界面看着像卡死了：

- `progress` 区永远停在「正在验证路径...」，一个不动的进度条
- `results` / `empty` / `actions` 三个区在 `startDupScan` 开头就被藏了，启动失败时
  **一个都没放回来**，整块内容区空白

错误确实写进了状态栏，但状态栏在 `progress` 区里面，用户第一眼看到的仍是空进度条。

`startDupScan` 一进来做的 3 个改动（`results`/`empty` 隐藏 + `progress` 显示）只在
「扫描成功启动」时才是对的。成功路径的收尾在 `finishDupScan`，而启动失败的**两条早退
路径**（后端返回 `error` / 请求抛异常）原本一个都没还原。现在两条都调
`restoreDupScanUI()`，把 progress、文案、计数、按钮、空态区全部还原，空态标题顺便
写明原因。

顺带三处：

1. **`AbortError` 单独识别**。`API.post` 默认 30s 超时，目录太大时启动请求本身可能就慢，
   但对用户来说结果是「没开始扫描」，不该表现成英文的 `signal is aborted` —— 现在说
   「启动扫描超时(30s), 目录可能过大」
2. **成功路径也要清进度文案**。`finishDupScan` 移除了 `visible` 却没改文案，下次
   `startDupScan` 开头重设「正在验证路径...」时，中间会闪出上一次的旧内容
   （比如「正在计算哈希值 812/1000」）。这是浏览器实测发现的 —— 单元测试当时只查了失败路径
3. 空态区的 `h3` / `p` 会被写成失败原因，目录不存在时它是唯一能承载解释的地方

测试 `test_dup_scan_fail_restore.js` 9 项，用 happy-dom **真执行** `startDupScan`
（静态断言查不出「哪条路径忘了还原」），覆盖：后端返回错误 / 请求抛异常 / AbortError /
成功路径不被误伤 / 幂等 / 两条路径都清了文案。7 项故障注入全抓到。

顺带说明：`empty`（空目录）分区虽然长得像，但它的失败都走 `finishEmptyScan(false, ...)`，
那条路径已经会移除 `visible`，没有这个问题。

## 布局：7 个面板里 4 个挂到了 body 下

用户报「去重、相似等卡片右侧超出了上面文件体检卡片」。实测（1280px 视口）：

```
.tabs（导航区）        left=51   right=1219   宽 1168
.tab-panel.active   left=0    right=1270   宽 1270   ← 撑满全屏
inner-tabs（面板内）    16  ~  1254        ← 右侧多 35px、左侧多 35px
```

根因：`index.html` 里 `.tabs` **提前闭合**（`</div><!-- Panel: tmp -->` 前面多了一个
`</div>`），于是 7 个 `tab-panel` 里有 **4 个**（scan / sysjunk / schedule / diskanalysis）
成了 `<body>` 的直接子元素，`.footer` 也是。`<body>` 有 `position:relative` 且无宽度约束，
宽度就是整个视口；而 `.tabs` 在 `.container`（`max-width:1200`）内只有 1168px。

**修法（改 HTML 根治）**：删掉提前闭合的 2 个 `</div>`；在最后一个 panel 之后、
第一个 modal 之前闭合 `.tabs`；`footer` 之后闭合 `.container`；顺带把
`<dialog id="simdupCompareDlg">` 从两个 panel 之间挪进 `scan` 面板内（它原本插在
scan 和 sysjunk 中间，成了 `.tabs` 的直接子元素）。

`switchTab` / `switchInnerTab` 都用 `querySelector` 按 `data-panel` 定位，不依赖父级，
移动面板位置不影响功能。修后浏览器实测 7 个 tab 的父级均为 `tabs`、全后代溢出 0。

**绕路的教训**：最初想用 CSS 补丁（`.tab-panel` 加 `max-width` + 16px 横向 padding）绕过，
结果引入了**新的不一致** —— 补丁给所有面板都加了 16px padding，导致 `.tabs` 内的面板
（app/disk/docker）内容缩进 16px，而 body 下的那批对齐，**切 tab 时左右边界会跳动 16px**。
CSS 绕不过结构问题，只会在旁边制造新 bug。结构修好后 CSS 补丁已撤掉，并有测试守着不让它复活。

### CSS 是 7 天强缓存

```
$ curl -sI .../styles/style.css | grep -i cache
Cache-Control: public, max-age=604800, immutable
```

服务端**没有**缓存（实测移除规则后返回的 CSS 短了 101 字节），是浏览器按 `immutable`
缓存了。`index.html` 写的是 `styles/style.css?v=3`，这个 `?v=` 就是唯一的失效手段 ——
**改了 CSS 不 bump，浏览器 7 天内一直用旧样式**，表现为「代码明明改了，界面却没变化」。

对比静态文件时**必须 bump `?v=` 或用全新浏览器 session**，否则测的是缓存。

## v0.11.2 更新

本版聚焦**性能对齐行业基线**、**删除安全**、**多目录选择**与**移动端可用性**。

### 性能：哈希并发按介质自适应

- **问题** — 哈希 worker 原硬编码 4 个。本机是 **Intel Celeron J3355 双核** +
  `sda`/`sdb` **机械盘 RAID1**(WD43PURZ) + `sdc` 固态盘，固定 4 既是 2 倍 CPU 超订，
  又让机械盘多线程随机读产生寻道竞争。fclones 官方文档明确建议机械盘用
  `--threads 1`，并报告过 2x~10x 的性能差异。
- **修复** — 新增 `app/storage_profile.js`，读 `/sys/block/<dev>/queue/rotational`
  判定扫描目标所在卷的介质类型（自动穿透 LVM / device-mapper）：
  **机械盘降为单线程 / 固态盘取 `min(4, CPU 核数)` / 介质无法确定时保守按机械盘处理 /
  多路径混合时取更保守的一侧**。推导结果写入任务状态并输出日志：
  `[dup_scan] 哈希并发度=1 · 机械盘(/vol2) — 单线程避免寻道竞争`

### 性能：partial 预筛采样量 4KB → 32KB

- 每段 4KB 区分度不足，MP4/MOV/ISO/压缩包文件头高度雷同，大量文件被迫进入全量哈希。
- 改为**头尾各 32KB（合计 64KB）**，对齐 file-deduplicator 的头尾 64KiB 水平。
- **只加大单段读取、保持 seek 次数恒为 2** —— 机械盘上多一次 seek 的成本（数毫秒）
  远高于多读几十 KB，因此**不加**中段采样点。

### 🔒 安全：保护 fnOS 系统目录与卷内回收站（P0）

- **问题** — 删除校验的白名单只到卷粒度（`/vol*`），导致
  `/vol3/@appcenter`（**所有应用的安装目录**）、`@appdata`、`@appmeta`、`@apphome`、
  `@appconf`、`@appshare`、`@apptemp`、`@sysappmeta`，以及 `/volN/<uid>/.@#local`
  （**卷内回收站**）**全部通过校验**。重复扫描命中各应用的同名 LICENSE/图标后勾选删除，
  会**误删其他应用文件导致应用起不来**。
- **修复** — 用**精确名单**（非 `@` 前缀正则，避免误伤用户自建的 `/vol1/1000/@我的相册`）
  拦截上述 8 个系统目录 + 回收站；删除/大文件/空目录三个端点接入并回传**拦截数量与逐条原因**，
  前端明确提示「N 个受保护未删除」。
- **刻意不接入应用卸载器**(`app.js`) —— 它的语义就是卸载应用（删除目标本就是 `@appcenter`），
  接入会废掉卸载能力；只读端点不接入（仍可「看到」系统目录里的重复文件，只是删不掉）。
- **自身数据目录差异化豁免** — 读写场景豁免（要写哈希缓存/manifest/导出），
  删除场景**一律不豁免**（否则清理工具会把自己的缓存和审计清单一起删）。

### 🚀 扫描排除规则（可自定义）

- **问题** — 原先扫描除最小体积外无任何路径排除，每次扫 `/vol1` 都要把 `@appdata`
  的 SQLite、`node_modules`、`.git`、Docker overlay 全走一遍；哈希缓存虽能跳过重复计算，
  但 `walk + statSync` 的元数据开销跑不掉，且系统目录里发现的"重复文件"多半是各应用
  共用的 LICENSE/图标，对清理没有价值。对标 fclones 的 `.hashignore`。
- **修复** — 新增零依赖 `app/exclude_rules.js`，`dup_scan` 与 `simdup_scan`
  在 **readdir 之后、stat 之前**剪枝（目录整棵跳过）；规则落盘
  `<TRM_PKGVAR>/data/scan_exclude.json`，`GET/POST /api/dup/exclude-rules` 读写，
  重复文件面板提供折叠式编辑区（展开时才懒加载）。
- **匹配语义** — 不含 `/` 的规则按**路径段**匹配（任意层级，支持 `*` `?`）；

## 功能特性

- **自动扫描** — 动态发现系统中所有 vol 卷（`/vol1` ~ `/vol10` 及 `@app*` 目录）
- **孤立目录检测** — 交叉比对已安装应用列表与实际文件目录，精准识别残留孤立目录
- **多选删除** — 支持批量勾选，一键清理，附确认弹窗与路径预览
- **明暗主题** — 支持手动切换（深色/浅色）
- **Tab 切换** — 应用 / 网盘 / Docker / tmp / 去重 / 去空 / 系统清理 / 回收站 独立展示
- **KPI 卡片** — 显示卷总数、已挂载数量、未挂载数量
- **Docker 卷管理** — 查看在用卷/残余卷，一键批量删除
- **Docker 网络管理** — 扫描未使用网络，一键批量删除
- **Docker 镜像管理** — 查看未使用镜像，一键批量删除
- **tmp 清理** — 扫描 `/tmp` 和 `/var/tmp` 下 24h+ 未访问的文件，一键清理
- **文件去重** — SHA-256 哈希比对，智能分组显示重复文件
- **音乐去重** — 基于元数据（ID3/FLAC）的智能重复音乐识别
- **去重多线程哈希** — 10 线程并行计算文件哈希，动态调度；**首尾双段 4KB 预哈希**（Czkawka 风格）跳过头同尾不同文件
- **空目录清理** — 扫描指定目录下的空目录（全空目录合并显示），支持回收站/永久删除
- **目录浏览选择** — 内置文件选择器，支持浏览并选择扫描目录
- **系统清理** — 17 项扫描目标（apt / syslog / journal / 包管理器缓存 / 浏览器 / Playwright / 旧内核），三档风险过滤 + 一键推荐清理 + 清理前 manifest 备份 + **5 类分类浏览**（系统/日志/开发/浏览器/应用）
- **回收站批量清理** — 扫描所有 vol × 所有 UID 的 `.@#local/trash/`，按 mtime 30/90/365 天分级清理，root 权限包含全部用户
- **启动警告弹窗** — 每次进入应用立即弹「⚠️ 清理有风险」红底警示（3 秒倒计时）
- **响应式布局** — 适配桌面端与移动端
- **磁盘空间分析** — 卷用量总览 + 目录下钻排行 + 文件类型分布 + 顶层大文件（P0-1）
- **相似图片/视频检测** — 感知哈希识别同图不同分辨率/水印、同视频不同转码（P0-2）
- **异常文件检测** — 空文件/无效软链接/损坏媒体/下载残留识别（P0-3 + P2-1）
- **重名冲突检测** — 找出跨目录同名文件分组（不区分大小写，P2-2）
- **轻量架构** — 纯 Node.js ESM 实现，零 npm 依赖

- **通信**：HTTP API 请求 + UNIX Socket（fnOS Gateway 转发）
- **数据存储**：JSON 文件状态 + 去重结果持久化
- **fnOS Gateway**：自动挂载 `/app/fnclearup` 前缀
- **依赖**：需 Node.js v24 运行时

  GET/POST /api/dup/exclude-rules 读写, 面板提供折叠式编辑区(展开时懒加载)。
- 默认 18 条含 @app*/@sysapp*(覆盖 fnOS 全部 8 个系统目录)与 node_modules/.git/__pycache__/
  lost+found/overlay2 等。刻意不用 @* —— 会误伤用户自建的 /vol1/1000/@我的相册。

**保护 fnOS 系统目录与卷内回收站(删除安全, P0)**

  @appmeta、@apphome、@appconf、@appshare、@apptemp、@sysappmeta 与卷内回收站

### v0.11.2

**哈希并发按介质自适应(不再固定 4 worker)**

- 问题: 哈希 worker 原硬编码为 4 个。本机是 Intel Celeron J3355 **双核** +
  `sda`/`sdb` **机械盘 RAID1**(WD43PURZ) + `sdc` 固态盘,固定 4 既是 2 倍 CPU
  超订,又让机械盘多线程随机读产生寻道竞争。fclones 官方文档明确建议机械盘用
  `--threads 1`,并报告过 2x~10x 的性能差异。
- 修复: 新增 `app/storage_profile.js`,读 `/sys/block/<dev>/queue/rotational`
  判定扫描目标所在卷的介质类型(自动穿透 LVM / device-mapper),
  机械盘降为单线程、固态盘取 `min(4, CPU 核数)`、介质无法确定时保守按机械盘处理、
  多路径混合时取更保守的一侧。推导结果写入任务状态 `storageProfile` 并输出日志:
  `[dup_scan] 哈希并发度=1 · 机械盘(/vol2) — 单线程避免寻道竞争`

**partial 预筛采样量 4KB → 32KB(头尾各一段)**

- 问题: 每段仅取 4KB,区分度不足,MP4/MOV/ISO/压缩包这类文件头高度雷同,
  大量文件被迫进入全量 SHA-256。
- 修复: 每段 4KB → 32KB(头尾合计 8KB → 64KB),对齐 file-deduplicator 的
  头尾 64KiB 水平。**只加大单段读取、保持 seek 次数恒为 2** —— 机械盘上多一次
  seek 的成本(数毫秒)远高于多读几十 KB,因此不加中段采样点。

  用户勾选删除即会**误删其他应用的文件,导致对应应用无法启动**。
