# USB Rsync — Node.js 版 (v0.5.1)

> USB 存储设备自动同步工具，检测到 USB 设备插入后自动同步指定目录，支持单向和双向同步模式。
> **Node.js 重写版** — 由 bash CGI + bash 守护架构迁移为纯 Node.js 单进程架构。

## 架构变化 (vs 原 CGI 版)

| 原版 (usbrsync-cgi) | Node.js 版 (usbrsync) |
|---------------------|----------------------|
| bash CGI (`index.cgi` + `api.sh`) | **Node HTTP server** (`ui/server.js`) |
| bash `cmd/main` 守护 (mount_monitor) | **Node 守护** (`ui/daemon.js`, 内嵌于 server) |
| 状态文件共享 (sync.pid/status.json) | 进程内状态 + 磁盘持久化 |
| 每请求起 bash 进程 | 常驻 HTTP server (socket 模式) |
| `ui/server.js` 单进程 = HTTP + USB 监控 + 计划调度 | — |
| rsync 执行 `ui/rsync.js` | — |

**核心优势**：
- 单进程，无 CGI 进程开销，事件驱动并发安全
- USB 监控、计划调度、HTTP 服务内存共享状态，无磁盘竞争
- 原生 `spawn` 管理 rsync 子进程，进度/停止/双向更可靠
- fnOS 标准 socket 模式部署

## 功能 (与原版完全一致)

- **任务 CRUD** — 添加/编辑/复制/删除/排序同步任务
- **自动同步** — USB 插入检测 + UUID 绑定设备 + `auto_sync_on_insert`
- **计划同步** — 每日/每周定时 (cmd 配置)
- **同步模式** — 单向/双向、`--delete`、`--checksum`、重试+间隔、空间检查
- **保留历史** — `--backup --backup-dir=.rsync-history/<时间戳>` (keep_history)
- **反向恢复** — 任务卡「恢复」按钮，备份目标 → 源
- **源/目标对比** — 「对比」按钮 + 同步后自动差异写入历史
- **exFAT/NTFS 兼容** — 自动 `--modify-window=1`
- **预览** — dry-run 统计新增/修改/删除
- **日志** — sync.log 实时追踪 + 5MB 轮转
- **历史** — 100 条上限 + 成功/失败/字节/耗时
- **统计** — KPI 仪表盘
- **fnOS 通知** — 同步完成/失败发桌面铃铛
- **配置导出/导入** — JSON
- **响应式 UI** — 桌面+移动端

## 版本历史

### v0.5.1 — 大容量 U 盘「源目录无权限」修复

大容量 U 盘（exFAT / NTFS，如 /dev/sdg）在「源目录」浏览时显示无权限，
小容量 U 盘却正常。根因是这两类盘的文件系统驱动不同：小盘多是 FAT32 走内核
`vfat`，挂载时带 `uid=/fmask`，谁都能读；大盘走 `fuse`（`lsblk` 里是
`fuseblk` / `fuse.exfat` / `fuse.ntfs-3g`），而 fuse 默认**只允许挂载它的那个
uid 访问，连 root 也会被拒**（挂载时没带 `allow_other` 的话）。

**按挂载 owner 降权读取（新增 `ui/mountperm.js`）**
- `parseMounts` 解析 `/proc/mounts`（含 `\040` 八进制转义）、`mountForPath` 最长前缀匹配
- `ownerUidOf` 取挂载 owner：① 挂载参数里的 `uid=/gid=` ② 持有该挂载的 fuse 守护进程 uid
- `listAsUid` 以该 uid 起子进程用 `ls -1ap` 列目录（末尾 `/` 标目录，免逐个 stat）
- `/api/browse` 遇 `EACCES/EPERM` 自动降权重列一次，成功则正常返回并带 `via: "uid:N(来源)"`
- rsync 侧同步支持：`preflight` 的 dry-run、正向同步、反向恢复三处 `spawn` 都带 `uid/gid`；
  `requestSync` 先探测 root 能否读源目录，读不到且挂载 owner 非 root 才降权（并写日志）

**允许范围**
- `isAllowedPath` 增加「当前挂载着的可移动/外接文件系统」动态放行：外接盘被挂到
  `/vol00` 以外（如 `/run/media`）时不再报 `root not allowed`
- `SYSTEM_MOUNT_DENY` 把 `/boot`（efi 是 vfat）、`/sys`、`/proc`、`/run`、`/usr` 等系统挂载排除

**错误说清楚（原来是死的 `not a directory`）**
- `EACCES` → 「没有读取权限（EACCES）：该盘由 uid=N 挂载，只有它能访问」
- `ENOENT` → 「目录不存在（设备可能已拔出）」；`ENOTDIR` → 「这不是一个目录」
- `/vol00` 下未挂载的占位目录（mode 000、空）→ 「设备未连接（这是挂载点占位目录…）」，
  以前 root 读得进去，界面显示成空文件夹，看着像盘里没东西
- 子项 `statSync` 失败不再拖垮整层目录

**新增自查接口 `GET /api/diag_usb`**
一次性摊开：`lsblk` 树（tran/rm/fstype/mountpoint）、`collectUsbMounts()` 结果、
每个设备的 `/proc/mounts` 原始行、挂载点 `stat`(mode/uid/gid)、`realpath`、
`readdir` 的真实 errno、`isAllowedPath` 判定、挂载 owner、按 owner 读取的探测结果，
以及 `/vol00` 每个占位目录的 mode 与 mounted 状态。盘插上后一句话就能定位。

**修复「设备未连接」误判正常卷目录（本条为 v0.5.1 内部的回归修复）**
fnOS 的用户卷目录大量是 `d---------+`（mode 000 + POSIX ACL，如 `/vol1/1000`、
`/vol1/1000/Photos`、`/vol1/1000/手机系统备份`）。最初的占位目录判断写成
「mode 000 且不是挂载点 → 设备未连接」，把这些正常目录全部误判了。
现收窄为：只有父目录是外接设备挂载根（`/^\/vol0+$/`，即 `/vol00`）、
该目录不在 `/proc/mounts` 里、且 mode 为 0，才算占位目录。

**测试**
- 新增 `tests/test_mountperm.js` 9 项（八进制转义、挂载解析、最长前缀匹配、`uid=` 优先、
  fuse 进程探测含假 `/proc`、非 fuse 返回 null、`listAsUid` 类型标记）
- `tests/test_api.js` 新增回归用例「mode 000 的普通目录仍可浏览（不得误判为设备占位）」
- 全量 101 项通过（api 26 + auto_sync 17 + mountperm 9 + rsync_guards 26 + usb_detect 23）

### v0.5.0 — 同步可靠性与数据安全（汇总 v0.4.3 → v0.4.11）

这一版把「插入就同步、跑完要能查、跑坏不能毁数据」这三件事做完了。

**数据安全（这是重点）**
- `--delete` 三重护栏：同步前先做一次 `rsync --dry-run --stats` 预检，
  ① 源目录里一个文件都没有却要删除目标内容 → 直接阻止（U 盘没挂稳、路径选错的典型场景）
  ② 预检要删的数量超过源文件数 5 倍 → 阻止
  ③ 带删除但预检本身失败 → fail-closed，宁可不跑
- 拦下来的原因写进状态栏和历史记录，不用翻日志也能看到为什么没同步
- 掉盘判定收窄：只有 `change_dir failed` 或源/目标根目录消失才算掉盘，
  单个文件消失（rsync 23/24）不再把整次同步判成失败
- 停止同步改为 SIGTERM → 等 10 秒 → SIGKILL，卡在 IO 上的 rsync 也能真的停住
- 单次执行 5 分钟无输出自动结束；日志按 64KB / 400ms 批量落盘，内存只留 256KB 尾部
- 保留历史时自动只留最近 10 份备份目录
- 源/目标不存在时直接拒绝并提示具体路径，不再让 rsync 以 23 退出留一条看不懂的记录

**插入自动同步**
- 守护重写：`requestSync` 只返回 `running|busy|error`，被「已有同步在跑」挡下的触发
  进入延迟队列，空闲后补跑（以前直接记成"已触发"，任务就这么静默丢了）
- 每任务 120 秒冷却窗口，U 盘抖动 / 重新枚举不会反复触发
- 触发前校验源、目标真实存在；UUID 大小写不敏感
- 待补同步每轮检查（不只在插入事件里），重试 ≥30 秒间隔、3 次后出队
- **修复挂载目录改名导致自动同步失效**：同一个 U 盘重插后 fnOS 可能换挂载目录名
  （实测 `/vol00/RemovableDisk_1` → `/vol00/ProductCode_1`），旧逻辑按路径前缀匹配
  永远失败且不写日志。现在按设备 UUID 匹配 + 按「设备内相对路径」自动换算
- 所有跳过分支都写日志（设备不匹配 / 路径无法换算 / 源目标缺失 / 冷却期）
- 新增 `GET /api/auto_sync_check` 与界面「自动同步检查」弹窗，逐条列出任务会不会触发、为什么

**进度 / 历史 / 统计**
- 进度：已传输 x/y、瞬时速度、已用时、剩余时间、本次传输文件数、待检查文件数
  （数据来自 rsync `--info=progress2` 与同步预检，进度条是真实 x/y）
- 历史：22 个字段，行内显示任务名、路径、耗时、文件数、流量、删除数、重试、均速、短状态标签；
  点开看退出码中文含义、开始/结束、本次需传输量、所用选项、剩余差异、错误原文（最多 5 条）；
  支持「全部 / 成功 / 失败」服务端筛选
- 历史记录显示**任务名称**，升级前的老记录按 task_id 回查任务表自动回填
- 统计：成功率、平均耗时/速度/字节、累计文件与删除数、近 24h 汇总、
  最近 7 天趋势、按任务聚合、失败原因 Top5

**界面**
- 设计系统 v2：品牌色/中性灰/语义色四类令牌，组件区零字面色值，深色与浅色主题对比度 ≥4.5:1

### v0.4.11 — 修复「插入后自动同步无效」

**根因**：任务里存的是源目录绝对路径，而同一个 U 盘重新插入后 fnOS 给的挂载目录名
会变（现场实测：`/vol00/RemovableDisk_1` → `/vol00/ProductCode_1`）。
原来的匹配条件是「源路径必须以本次挂载点为前缀」，挂载点一改名就永远匹配不上，
而且**失败时不写任何日志**，看起来像功能失效。

**修法**
- 匹配改为按**设备 UUID**（本来就是绑定的那个分区），不再要求路径前缀命中
- 路径自动换算：优先用保存的「设备内相对路径」`source_rel`；老任务没有该字段时，
  按「挂载父目录相同、第一段是旧挂载目录名」推断（`/vol00/RemovableDisk_1/DCIM`
  → `/vol00/ProductCode_1/DCIM`），换算后再校验目录真实存在
- 保存任务时自动记录 `source_rel` 与 `source_mount`，以后改名零推断
- 所有跳过分支都写日志：设备不匹配、路径无法换算、换算后目录不存在、
  冷却期、源/目标不存在，都能在 `usbrsync.log` 里看到原因
- 新增 `GET /api/auto_sync_check`：逐条列出每个任务是否会在插入后触发、匹配到的
  挂载点、换算后的源目录、以及不触发的具体原因
- UI 侧栏「同步任务」卡片新增 **自动同步检查** 按钮，弹窗展示上面这份判定结果

**实测**：本机 U 盘（UUID `5EF3-DE54`，卷标「新加卷」）当前挂在 `/vol00/ProductCode_1`，
任务源路径仍是 `/vol00/RemovableDisk_1`，修复后判定为「会触发」，换算后源目录
`/vol00/ProductCode_1`。

### v0.4.8 — 全面安全审计修复（数据安全 + 接口面 + 运维）

用 `code-audit` 审完全部 3,384 行后按严重度修（凭据类按用户要求保持不动）：

**数据安全（最关键）**
- `--delete` 加了预检护栏：同步前先跑一次 `rsync --dry-run --stats`，
  · 源侧正则文件数为 0 却要删东西 → 直接阻止（设备没就绪 / 路径选错 / 目录被清空）
  · 删除量 > 源文件数 × 5 → 阻止（疑似源路径选错）
  · 带删除且预检失败 → fail-closed，宁可不跑
  · 手动 / 插入自动 / 计划 / 待补 **四条路径统一走同一道关**
- 掉盘判定收窄：只有 `change_dir failed` 或源/目标根目录消失才算掉盘，
  单文件在同步中消失（rsync 23/24）不再整单判失败、不再白占待补重试次数
- 停止增加 SIGKILL 升级：SIGTERM 后 10 秒仍未退出则强杀（卡 IO 的 rsync 不理 TERM）

**接口面**
- `/sync_stop`、`/preview`、`/config_import` 必须 POST（原来 GET 即可触发状态变更）

### v0.4.7

> **关于运行权限**：本应用曾尝试改为 `package` 用户运行以降低 Web 层风险，实测不可行并已回退。
> 原因是 fnOS 的用户数据目录采用 `000 + ACL` 权限模型（`/vol1/1000` 的 ACL 为 `user::rwx group::--x other::--x`，
> 不含任何应用账号条目），`package` 落入 `other` 只有 `--x` —— 可进入目录但**无法 `readdir` 列目录**。
> 而本应用的核心功能（选择源/目标目录、rsync 增量比对）都依赖列目录，因此必须以 `root` 运行。
> 如需降低风险，建议改为**限制 Web 端暴露面**（绑定 `127.0.0.1` + 远程走 SSH 隧道），而非降权运行。
